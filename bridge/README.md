# ChatGPT Browser Bridge

This is a browser transport layer, not the primary control plane.
Core analysis, planning, and execution should happen locally first, with browser automation used only as a fallback delivery path.

## Flow

1. The engine parks a strategy signal at `GET /api/ai/pending`.
2. `bridge.js` connects to your logged-in Chrome tab on `chatgpt.com`.
3. The bridge pastes the prompt and waits for ChatGPT to return strict JSON.
4. The bridge posts the result to `POST /api/ai/bridge-result`.
5. The engine validates the result and executes the trade if approved.

## Required ChatGPT reply format

The engine now asks ChatGPT to return only:

```json
{
  "approved": true,
  "action": "BUY",
  "confidence": 0.91,
  "reason": "short reason"
}
```

## How to run

1. Start the engine.
2. In another terminal:

```powershell
cd bridge
node bridge.js
```

Or use:

```powershell
cd bridge
.\RAIG_ROBOT.ps1
```

## Test the bridge

Send a fake signal:

```powershell
Invoke-WebRequest -Method Post -Uri http://localhost:8080/api/ai/test-signal
```

Then watch the bridge terminal and engine logs.

## Bridge logs

Each bridge decision is appended to:

```text
bridge/bridge-decisions.jsonl
```

This file records parsed ChatGPT verdicts, engine submissions, and bridge errors.

## Session readiness checks

Before sending a signal, the bridge now checks whether ChatGPT is actually usable.

It will stop and log a clear error if:

- ChatGPT login is required
- access is blocked by verification/CAPTCHA
- the prompt box is missing

These conditions are written to `bridge/bridge-decisions.jsonl` as `bridge_error` entries.

## Automatic recovery

If the ChatGPT tab refreshes, navigates, or loses the active session, the bridge now tries to:

- re-find the ChatGPT tab
- bring it to the front
- verify the prompt box is usable again

Recovery attempts are also written to `bridge/bridge-decisions.jsonl`.

## Important limitations

- This depends on ChatGPT web UI selectors and can break when the site changes.
- Browser sessions can expire.
- Response timing is variable.
- Use paper trading only until you are confident in the loop.

## Autonomous repo handoff

The bridge folder now also includes `autonomous-handoff.js`, which consumes:

```text
output/autonomous_bot/browser_handoff.json
```

This is generated by:

```powershell
python autonomous_repo_bot.py
```

### What it does

1. Reads the prompt queue from `browser_handoff.json`
2. Syncs a persistent transport queue with stable item IDs
3. Opens a logged-in browser tab for ChatGPT or Claude
4. Submits each prompt one at a time
5. Waits for the assistant response
6. Saves the response into `output/autonomous_bot/browser_results/`
7. Updates `output/autonomous_bot/browser_status.json`
8. Records retry state in `output/autonomous_bot/browser_transport_queue.json`

### Run for ChatGPT

```powershell
cd bridge
npm run handoff:chatgpt
```

### Run for Claude

```powershell
cd bridge
npm run handoff:claude
```

### Optional flags

```powershell
node autonomous-handoff.js --provider chatgpt --limit 2
node autonomous-handoff.js --provider claude --continue-on-error
node autonomous-handoff.js --provider chatgpt --force
```

### Requirements

- Chrome must be running with remote debugging enabled:

```powershell
chrome.exe --remote-debugging-port=9222
```

- You must already be logged into the target AI site.
- The prompt queue must already exist under `output/autonomous_bot/`.

### Output files

- `output/autonomous_bot/browser_status.json`
- `output/autonomous_bot/browser_transport_queue.json`
- `output/autonomous_bot/browser_results/chatgpt/*.response.md`
- `output/autonomous_bot/browser_results/claude/*.response.md`
- `bridge/autonomous-handoff.log.jsonl`

### Retry behavior

- Each prompt gets a stable queue ID.
- Failures are classified, such as `timeout`, `submit_failed`, or `browser_unreachable`.
- Failed prompts get a bounded exponential backoff before retry.
- Use `--force` to retry immediately.
